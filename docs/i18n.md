# Internationalization (i18n)

OpenBin's client uses [react-i18next](https://react.i18next.com/) for translations. This is a **foundation**: only two namespaces exist so far (`common`, `auth`), covering the app shell/layout chrome and the auth flow, proven against one pilot locale (Norwegian, `nb`). The other ~25 feature folders still have hardcoded English strings — that's deliberate, not an oversight. See "Roadmap" below.

## Namespaces

- **`common`** (`src/locales/{lng}/common.json`) — shared layout chrome (`src/features/layout/`: sidebar, bottom nav, mobile drawer, create-FAB, app shell) **plus** generic cross-cutting strings used across the whole app: `actions.save`, `actions.cancel`, `actions.delete`, `actions.loading`, `actions.confirm`, etc. These generic keys are defined now — even though only a handful of call sites in this PR consume them — so that every future namespace PR can reuse them instead of re-defining (and later de-duplicating) the same generic keys namespace-by-namespace.
- **`auth`** (`src/locales/{lng}/auth.json`) — everything under `src/features/auth/`: login, register, forgot/reset password, complete-signup, social buttons, OAuth error toasts, consent checkboxes.

`common` is preloaded on app boot (`src/lib/i18n.ts`'s `ns: ['common']`) so the app shell never flashes untranslated keys. `auth` lazy-loads via `i18next-resources-to-backend` when the auth route first needs it.

As follow-up PRs migrate more feature folders (see Roadmap), each adds its own namespace JSON file and updates `src/i18next.d.ts`'s `resources` type (see below).

## Adding a new string

1. Add the key to the right `src/locales/en/{ns}.json` (and mirror it — even with a rough/untranslated placeholder — in `src/locales/nb/{ns}.json`; `i18next-cli lint`, wired into CI, flags missing keys).
2. In the component: `const { t } = useTranslation('common' | 'auth');` then `t('some.key')`.
3. Pass a `defaultValue` when the string also needs to render sensibly under the test mock (see Testing below): `t('some.key', { defaultValue: 'English text' })`.
4. If you're adding a **new namespace**, update `src/i18next.d.ts`'s `resources` map so `t()` calls stay type-checked against the real JSON shape.
5. If your file uses `useTerminology()` (the admin-configurable "bin"/"tote"/etc. term system), destructure it as `term`, not `t` — `const term = useTerminology();` — to avoid colliding with i18next's `t`. `useTerminology()` itself is a separate, non-i18n system (see "Known limitations" below); it isn't part of `common`/`auth` and doesn't need translation keys.

Nested JSON objects are the convention (e.g. `auth.login.emailLabel`), not flat dotted-string keys — this is idiomatic for i18next namespaces and lets `src/i18next.d.ts` generate a properly-nested key type.

## Extraction and lint tooling

This repo uses [`i18next-cli`](https://github.com/i18next/i18next-cli) (the maintained successor to `i18next-parser`), configured in `i18next.config.ts` at the repo root:

```sh
npx i18next-cli lint      # same check CI runs — flags hardcoded strings, missing/unused keys, interpolation mismatches
npx i18next-cli extract   # scans source for t()/useTranslation() calls and updates the JSON resource files
```

`i18next.config.ts`'s `extract.input` glob is scoped to the files this PR (and each namespace follow-up PR) actually migrated — not all of `src/`. The other ~25 feature folders still have hardcoded strings by design (see Roadmap), so widening the glob to include them before their own migration PR lands would make CI fail on pre-existing, not-yet-in-scope code. **Each follow-up PR should widen `extract.input` to include the folder(s) it migrates.**

## Adding a new locale

1. Create `src/locales/{code}/common.json` and `src/locales/{code}/auth.json` mirroring the `en/` files' key structure.
2. Add `{ code, label }` to `SUPPORTED_LANGUAGES` in `src/lib/language.ts` — `label` should be the language's **native** name (e.g. `"Norsk (bokmål)"`, not `"Norwegian"`) so users can find their language regardless of the app's current display language.
3. Add the code to the server's hardcoded allowlist in `server/src/routes/auth/profile.ts` (`SUPPORTED_LANGUAGE_CODES`) — `PUT /api/auth/profile` rejects any `language` value not on this list. A DB-configurable list was considered and rejected: with only a couple of locales, adding one more means shipping translation JSON anyway (a code change regardless), so a configurable list would solve a problem that doesn't exist yet.
4. If the locale is RTL (Arabic, Hebrew, Persian, Urdu, ...), add its code to `isRtlLocale()` in `src/lib/language.ts` — this flips `document.documentElement.dir`, but note that's the *only* RTL support that exists today (see Known limitations).

## Known limitations (accepted, not solved in this phase)

- **`useTerminology()` composition.** Admin-configured term pairs (e.g. renaming "bin" to "tote") are plain text substitutions, not CLDR-aware. Composing them into a translated non-English sentence (e.g. `` `${term.bin} details` `` rendered in Norwegian) can read grammatically awkward in heavily-inflected languages. Not solved here — flagged for whoever eventually tackles it.
- **Pluralization.** Only i18next's built-in CLDR plural suffixes are used (`itemCount_one` / `itemCount_other`), which covers English and Norwegian (both simple 2-form plural languages). No ICU MessageFormat plugin (`i18next-icu`) yet — add it if/when a complex-plural locale (Arabic's 6 forms, Polish's 4, etc.) enters scope.
- **Dates and numbers.** `Intl.DateTimeFormat`/`Intl.RelativeTimeFormat`/`Intl.NumberFormat` usage (e.g. `UsageHeatmap.tsx`, `BinUsageSection.tsx`) is out of scope for this foundation since `common`/`auth` don't touch those files. Whichever follow-up PR migrates the `usage` namespace should convert module-level `Intl.DateTimeFormat` instances to `useMemo(() => new Intl.DateTimeFormat(i18n.language, {...}), [i18n.language])`.
- **RTL layout.** Only `document.documentElement.dir` is wired (pre-paint script in `index.html` + `setLanguage()` in `src/lib/language.ts`). No Tailwind `rtl:` variants, no icon/flex-direction mirroring anywhere in the app. Full RTL layout is a separate future epic.
- **Transactional emails are not covered, ever.** Password reset, invite, and account-deletion emails (sent via Resend) are generated server-side where no client `i18next` instance exists. This framework does not cover them now, and none of the follow-up PRs below are planned to either — email localization would need its own future epic with server-side translation infrastructure.

## Testing

- **Default (mocked) — most component tests.** `src/test-setup.ts` mocks `react-i18next` globally: `useTranslation()` returns a `t` that resolves `(key, opts) => opts?.defaultValue ?? key`. This keeps the hundreds of existing component tests fast, without needing real translation resources loaded — but it means call sites that need to render sensible text under test **must** pass `defaultValue`, e.g. `t('login.signIn', { defaultValue: 'Sign In' })`. Note this mock does not interpolate `{{vars}}` inside `defaultValue` — if a string composes with a runtime value your test asserts on (like `useTerminology()`'s admin-configurable term), compose it in plain JS around a non-interpolated `t()` call instead of relying on i18next interpolation (see `src/features/layout/CreateFab.tsx`'s `newBinPrefix`/`createBinPrefix` keys for the pattern).
- **Real resources — `renderWithI18n()`.** `src/test/i18nTestUtils.tsx` spins up a dedicated i18next instance (via `createInstance()`, isolated from the app's own `src/lib/i18n.ts` singleton) with the actual `en`/`nb` `common.json` and `auth.json` loaded synchronously, and renders through a real `<I18nextProvider>`. Use this to catch broken keys, missing interpolation vars, or JSON typos that the mock wouldn't — see `src/test/__tests__/i18n.test.tsx` for real-render and pluralization examples. Since the global mock above applies file-wide via `test-setup.ts`, call `vi.unmock('react-i18next')` at the top of any test file that uses `renderWithI18n()`.
- No Suspense-boundary wrapping is needed in tests (`react: { useSuspense: false }` in `src/lib/i18n.ts`).

## Roadmap (follow-up PRs, not built in this one)

One PR per namespace/feature-folder group, roughly smallest/highest-value first:

`settings+onboarding+tour` → `dashboard+activity+locations+areas` → `checkouts+shopping-list+tags+qrcode+print` → `capture+photos+bulk-add+reorganize+admin` → `ai` → `bins+items+pins+checklist+attachments` → `legal` (translation-review-gated, likely last) → `src/ee/*`.

Each such PR: add its namespace JSON (en + nb), migrate the folder's hardcoded strings, do the `useTerminology()` → `term` rename for any file it touches, widen `i18next.config.ts`'s `extract.input` glob, add a `renderWithI18n()` smoke test, and update `src/i18next.d.ts`'s `resources` type.
